## 1. 현대 개발 환경과 커뮤니케이션 방식
* **환경의 변화:** 같은 사무실/시간대의 '동시 회의' 중심에서, 시간과 장소의 제약을 넘어서는 **'분산 협업 환경'**으로 전환되었습니다.
* **동기(Synchronous) 소통:**
   * **특징:** 실시간 대화 (Zoom 화상회의, 긴급 통화, Slack 실시간 채팅 등).
   * **장점:** 빠른 의사결정과 직관적 소통.
   * **단점:** 시간대 제약, 업무 흐름 끊김, 기록 부족.
* **비동기(Asynchronous) 소통:**
   * **특징:** 시간차를 둔 대화 (이메일, GitHub 이슈 코멘트, PR 코드 리뷰 등).
   * **장점:** 업무 유연성/몰입도 향상, 문서화/기록화, 글로벌 협업 용이.
   * **단점:** 느린 피드백 루프, 텍스트 기반으로 인한 오해 가능성.

---

## 2. 비동기 협업의 5대 핵심 원칙
1. **Default to Async (기본은 비동기):** 단순 정보 공유나 상태 업데이트(데일리 스크럼 등)는 비동기로 처리하고, 긴급 이슈나 복잡한 의사결정에만 동기적 방식을 사용합니다.
2. **Write Things Down (모든 것을 기록하라):** 결정 사항, 아키텍처 설계, API 명세 등을 문서화하여 영구적이고 검색 가능한 지식 자산으로 만듭니다.
3. **Transparency (투명성):** 개인간의 은밀한 대화(Private DM)를 지양하고, Public Channel에서 소통하여 지식 공유와 검색 가능성을 높입니다.
4. **Over-communicate (과잉 소통):** 애매한 표현을 피하고, 관련된 모든 맥락(Context)과 예상 응답 기한(Timeline)을 포함하여 구체적으로 전달해야 오해를 줄일 수 있습니다.
5. **Respect Time Zones (시간대 존중):** 상대방의 근무 시간을 고려하여 비동기적으로 일정을 제안하고, 공통 근무 시간(Core Hours)을 활용합니다.

---

## 3. 비동기 협업 도구 (Tools)
* **GitHub Discussions:** 실행 가능한 작업(버그/기능)을 다루는 'Issue'와 달리, 질문이나 아이디어 등의 '열린 토론'을 위한 공간입니다.
* **GitHub Wiki:** 프로젝트 문서, 온보딩 가이드, 아키텍처, API 명세 등을 구축하는 지식 베이스입니다.
* **ADR (Architecture Decision Records):** "왜 이 기술을 선택했는가?"에 대한 과거/현재의 기술적 결정과 배경을 불변의 문서로 기록합니다.
* **RFC (Request for Comments):** 주요 변경사항 도입 전, 설계를 공유하고 미래를 위한 피드백과 기술적 합의를 도출합니다.
